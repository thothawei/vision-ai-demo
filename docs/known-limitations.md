# 已知限制

本文件說明使用系統時需要知道的限制與注意事項。開發者才需要的實作陷阱見 [CLAUDE.md](../CLAUDE.md)；各項數字的實測來源見 [dev/test-log.md](dev/test-log.md)。

## 辨識準確度與適用範圍

- **計數與尺寸量測（M2）**
  - 計數假設零件在畫面中佔少數像素、與背景亮度反差明顯；零件間距小於約 25px 時可能分不開。
  - 量測在正視角下實測誤差約 0.3–0.6mm（50mm 零件上約 1%），假設待測物與 ArUco 標記共平面；手機斜角拍攝誤差會變大。預設公差 1.0mm。
- **七段顯示器（M7）**：假設乾淨的分段字型。實測合成圖 0–9 全對，但**尚未用真實 LED/LCD 照片測試**；反光、模糊、角度歪斜、數字間距很近或小數點位置特殊時可能誤讀。
- **指針錶（M7）**
  - 找不到明顯外框圓時，需手動輸入圓心 `center_x/center_y`。
  - 指針是「通過軸心的長直線，針尖取延伸較長的一端」：配重比指針長的少見款式會判反；單一錶面有多根指針時只取最明顯的一根。
  - 角度校正（min_angle/max_angle）需自行量測換算。
  - 指針落在量測弧之外的「死區」時，讀值會夾在最近的邊界值，不會提示「指針不在刻度範圍」。
- **安全帽偵測（M5）**：資料集只有 helmet／head 兩類，**沒有反光背心類別**。
- **危險區域短影片**：以每隔 `sample_interval_s`（預設 1 秒）抽一幀，不是逐幀分析；快速通過的違規可能漏判。超過 `max_duration_s`（預設 60 秒）的內容不處理。
- **組裝防呆（M10）**
  - 只回報 OK/NG 與相似度，不會說明是缺件、裝反還是髒污反光；請看標註圖紅框人工判斷。
  - 每個料號只支援一個拍攝角度；需要多角度時，請以不同料號名稱各建一組黃金樣本。
  - 對齊失敗（照片與黃金樣本差異過大）會回 `INFO`，不會硬判 OK/NG。
- **色差（M11）**：假設整張照片光源均勻；標準色區與量測區若分別在陰影或反光處，同色也可能量出明顯 ΔE。
- **包裝追溯碼檢核（M8-1）與出貨標籤比對（M12）**
  - M8-1 只做字串／日期完全相等比對（大小寫正規化後）；OCR 或 AI 抽取有任何字元誤差（例如 O/0 混淆）都會判「不一致」而 NG，請人工核對「問題」欄位。
  - M12 只有批號可信任條碼；料號與數量完全依賴 OCR／AI，字跡模糊或反光會讀錯並判 NG。
- **文件結構化（M4）**：「數字來源核對」只在 OCR 模式有效；端到端模式沒有獨立 OCR 原文可核對，欄位會標示「無法驗證」。端到端模式較慢。
- **醫學影像分類展示（M8-2）**：**僅供技術展示，非醫療診斷用途。** 測試集 ACC=0.8862、AUC=0.9346；正常影像召回率僅 74.8%（約每 4 張正常片有 1 張被誤判為肺炎樣態），肺炎召回率 96.9%。

## 尚未用真實照片驗證

- M10 組裝防呆、M11 色差、M2 尺寸量測、M12 出貨標籤：只以合成圖驗證（公開網路上找不到合用的真實照片，`docs/evaluation.md` 標示「待補真實照片」）。
- **七段顯示器、指針錶、零件計數：已用 Wikimedia Commons 的真實照片實測；三者都已改善，其中零件計數仍有明顯限制**（2026-10-12，`docs/evaluation.md`）。七段顯示器：判讀流程重寫後 8 張中 5 張正確（重寫前 0/8；剩下 3 張是兩張完整場景照，與一張暗淡的細線 LED 計算機，後者有 3 個數字標成 `?` 交人工、沒有讀錯），**顯示器必須近拍並占滿大部分畫面**，完整場景照會讀錯；零件計數：分割重寫後 12 張中 7 張數對、1 張明確拒絕（重寫前 1/12；回報過 15、63、81、115 個）。**仍會數錯**：互相疊壓的零件堆（螺栓螺帽 3／9）、金屬零件放在近似色背景上（五金件 21／7）、嵌套的中空零件（同心 O 形環併成 1 個）、細長引線的電阻偶爾多切一個；零件必須放在素色背景上、四周留白（零件占滿畫面時會回 422 拒絕），零件太小要調低 `min_area_ratio`；指針錶：偵測流程重寫後 6 張全部在容許誤差內（重寫前 2/6；其中 3 張是改完才加入的留出照片，3/3），**但樣本只有 6 張、標註是目視讀值，不能當作精確的準確率**；已知未處理的情況：同一錶面有兩根重疊或接近的指針、一張照片裡有多個錶、明顯傾斜的斜拍（會讀偏）。合成圖上「全對」的結果**不能代表真實照片的準確度**，導入前務必用自家設備的照片重新評估，並預期需要調整演算法（例如七段的自適應二值化與透視校正、指針錶自動找刻度、計數的背景分割）。這批照片是網路公開照片，不是產線相機拍的，樣本數也少（3–8 張），結論是「明顯有問題」而不是精確的準確率。
- 瀏覽器拍照：只用 headless Chromium 的假相機驗證完整流程，真實手機／筆電相機的畫質、對焦、權限提示互動未實測。
- ERP 串接：C# 範例可編譯，但未對真實 SQL Server 端到端實測。

## 效能與資源

- 本機模型延遲：`qwen3.5:9b` 在 M1 Pro 上單次辨識約 8–20 秒（離線換取的代價）。
- 16GB 記憶體：同時載入 Ollama 與 PyTorch 模型會吃緊，模型皆首次呼叫才載入。
- 外觀異常檢測（M3）擬合固定用 CPU（此演算法在 MPS 上反而更慢）。耗時隨良品張數增加：metal_nut（220 張）5.4 分鐘、screw（320 張）11.1 分鐘、tile（230 張）6.8 分鐘，CPU 佔用可能到 400–500%。
- 監督式訓練耗時差異大：PCB（1000 張）32 分鐘；安全帽（5297 張）在 MPS 上 60 epoch 約 4.15 小時。
- Gemini 免費層（可選備援）速率限制：RPM=5、RPD=20；且免費層輸入可能被 Google 用於改進產品，請勿送出敏感影像。

## 自訂類別與資料回流

- 自訂類別的異常分數是 PatchCore 原始距離值，**不同類別之間不能直接比較**，每個類別的門檻獨立計算。
- 擬合佇列在記憶體中，**伺服器重啟會遺失排隊中的工作**；狀態卡在 `fitting` 時請重新上傳。
- `export_reviewed.py` 匯出的框是 AI 當時的預測，品質取決於當時的模型；它省下的是「從零開始框」的時間，不是校正時間。

## 可靠性與背景工作

- **單一程序**：同一個資料庫同一時間只能有一個服務程序（啟動時以 `<資料庫>.lock` 檔案鎖強制，拿不到鎖就拒絕啟動）；不支援多個 uvicorn worker，也不能在同一個資料庫上多開實例。
- 重啟時「正在做」的擬合一律標成已中斷，需要人按重試（不會自動從中斷點續跑，而是用已存的照片整個重新擬合）；程序被 `kill -9` 時擬合的子計算沒有被清理，只是狀態被標成中斷。
- webhook 有一個未修補的缺口：NG 通知先用背景執行緒直接送，送失敗才寫進佇列；程序在「紀錄寫入」與「送出失敗」之間被終止，這一筆通知既沒送出也沒進佇列。已在佇列裡的通知重啟後照常重試。ERP 一定要用 `since_id` 輪詢當保底。
- 健康檢查與功能可用性只檢查「條件是否具備」（檔案存在、Ollama 有回應且模型已下載、資料庫可寫），不會真的跑一次辨識；權重檔存在但內容損毀，要到第一次使用（完整性驗證）才會發現。
- `/readyz`、`/healthz` 是公開端點（只回摘要）；`/metrics` 需要 `X-API-Key` 或 qc 以上登入，Prometheus 內建的 `authorization` 不能帶這個 header（見管理者手冊）。
- 指標是程序內計數，重啟歸零。
- 磁碟空間檢查只看圖片所在的磁碟，低於 1GB 才警告。

## 模型、備份與資料保存

- 模型完整性檢查（SHA-256）每個程序、每個版本只做一次（首次載入時）；服務執行中被改動的權重檔，要到下次重啟才會被發現。
- 就地登錄的內建權重（v1）不要再原地覆寫，否則 SHA-256 不符會拒絕載入；要更新請登錄新版本。
- 異常檢測的權重是 pickle 檔，所以權重只能由伺服器端腳本登錄，網頁不提供上傳。
- `train_anomaly.py`（內建三個 MVTec 類別）改成寫進登錄庫的新版本資料夾後，**尚未重新跑過完整擬合**（約 5–11 分鐘一個類別）；網頁上傳自訂類別的擬合流程則已實跑驗證。
- 備份檔含使用者密碼雜湊；模型權重預設不備份；還原要先停止服務；沒有備份 `.env`（祕密請另外保管）。
- 圖片清理刪掉的檔案無法復原（所以預設只預覽）；清掉的圖片無法再用於複判資料回流與再訓練。
- 資料庫 schema 不支援降版；備份來自較新版本的程式時，還原會被拒絕。
- 模型說明卡的 defect、ppe 指標取自開發紀錄（沒有機器可讀的測試集指標檔），已標明出處。

## SPC 與報表

- 量測值從 0.20.0 起才隨每次辨識記錄；更早的紀錄需執行 `scripts/backfill_measurements.py` 才會進 SPC，而且尺寸量測當時沒存公差，補進來的長度與寬度沒有規格上下限。
- 尺寸的孔徑只在恰好偵測到一個孔時記錄；多孔的工件不會有孔徑的 SPC。
- X̄-R 的子群以「連續時間順序」切分，不區分批號或站別（可用站別、日期篩選縮小範圍）；不足一組的尾端不納入。
- Cp／Cpk 假設資料近似常態且製程穩定；子群少於 25 組只供參考；管制圖出現規則觸發點時，能力指標不應直接採信。
- Western Electric 規則 4 預設用 8 點（原始定義），可在畫面調整；其他規則的界線固定為 1σ／2σ／3σ。
- 報表的 Cpk 摘要每個（料號，特性）用期間內全部資料計算（資料 ≥ 10 筆用 X̄-R n=5，否則 I-MR），不分站別。
- 報表排程只提供 macOS launchd 的範例與 Windows 工作排程器的設定說明，Windows 未實測。

## 配方與主檔

- 依配方檢驗是**同步**執行（沒有背景排隊）；含 AI 步驟時可能要數十秒。
- NG 的 webhook 仍是「每個 NG 步驟」各一次，沒有整次配方檢驗層級的 webhook；ERP 要整次結果請輪詢 `GET /api/runs`。
- 複判是逐步驟做的；整次配方檢驗的「最終判定」由各步驟的最終判定動態合併，沒有整次層級的複判。
- 配方的圖片槽只是名稱，不檢查該槽的圖片內容是否符合步驟預期（例如把背面照放到正面槽）。
- 配方步驟的動態表單只處理數字、文字、勾選，其餘（座標、Lab 陣列）用 JSON 文字框輸入。
- 看板「整次配方檢驗」視角不套用模組篩選；紀錄表仍是單筆辨識。
- 批號是否屬於某工單不做驗證（主檔的批號只用來自動帶入）。

## 追溯資訊與整合

- 追溯資訊列可以選主檔的工單（自動帶入料號與批號）；也允許手動輸入，但不在主檔的工單號會被標記為臨時檢驗，且工單號大小寫視為不同（`WO-2026-0001` 與 `wo-2026-0001` 是不同工單）。
- ERP 串接：
  - `webhook` 是保底通知而非唯一來源。服務重啟後仍在重試佇列的項目、或重試超過 5 次放棄的項目，需由 ERP 端以 `since_id` 輪詢補齊。
  - API key 只接受 `X-API-Key` header，且只能辨識與唯讀（不能複判、不能管理）。
- 修改 `.env` 的 `CORS_ORIGINS` 需**重啟服務**才生效。
- 上傳大小檢查（`MAX_UPLOAD_MB`）發生在檔案讀入記憶體之後；面對不受信任的網路，請在反向代理層（如 nginx）另設請求大小上限。
- 批次上傳：整批共用同一組額外參數（例如同一個異常檢測類別、同一個危險區域），無法每張各自設定。
- 資料夾監控（`scripts/watch_folder.py`）單執行緒逐檔處理，量大時會排隊；處理中被中斷的檔案需手動搬回 inbox。
- 看板的「NG 原因柏拉圖」涵蓋所有會判 NG 的功能。例外：0.17.0 之前記錄的「尺寸量測超差」不會出現在柏拉圖（當時沒有存超差項目）；其他功能的歷史紀錄會一併反映。
- 批次 API 對不認得的參數回 422（不再靜默忽略）；資料夾監控腳本若帶了該動作不接受的參數，該張會失敗。
- 帳號與登入：
  - 目前是本機帳號與三種角色，沒有 SSO／LDAP。
  - 沒有「首次登入強制改密碼」；密碼規則只要求至少 10 個字元。
  - 登入失敗鎖定是針對帳號（預設連續 5 次失敗鎖 15 分鐘），沒有針對來源 IP 的限制。
  - 0.18.0 之前建立的檢驗紀錄沒有 `created_by`：operator 看不到，qc／admin 看得到。
  - 單機辨識分頁的色差標準仍是每次檢驗傳入；要有可稽核的標準，請把色差設成配方步驟（標準隨版本保存並記入稽核）。
  - 反向代理若改寫 `Host`，跨網站寫入檢查（Origin 必須與 Host 一致）可能誤擋，請保留原始 Host。

## 部署與整合驗證範圍

- **容器**：只在 arm64（Apple Silicon）macOS 的 Docker Desktop 實測；Colima／Podman、x86_64 Linux、Windows 沒有測。
- **容器內的 LLM**：只驗證 `app` 能連到 `ollama` 容器、系統狀態頁能正確回報「模型沒下載」；**沒有在容器內拉 6GB 的 `qwen3.5:9b` 並跑 LLM 功能**。
- **ERP 對 SQL Server**：Apple Silicon 上 SQL Server 容器無法啟動，C# 範例沒有對真的 SQL Server 實跑；輪詢邏輯以 SQLite 版端到端測試驗證（見 erp-integration.md「端到端驗證」）。
- **Windows**：未實測，見管理者手冊「Windows 部署」。
- **效能基準**（規劃書中的可選項）：這個版本沒有做，沒有任何各模組延遲的發布數字；ONNX 匯出因此也沒有納入。
